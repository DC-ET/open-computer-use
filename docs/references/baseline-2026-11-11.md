## 发现的问题

### 1. `make stress` 在系统 bash 下直接崩溃（P1，阻断）

`scripts/run-tool-stress-tests.sh:32` 的 `swift build "${build_args[@]}"` 在 `set -u` 下展开空数组，
系统 bash 3.2 会报 `build_args[@]: unbound variable`，脚本以 1 退出。默认 `debug` 配置必现；
`release` 配置因为数组非空可以绕过。这与 `a632ca7 fix(build): keep an empty keychain argument list
valid on bash 3.2` 是同一类问题。

本次基线的 20 轮 stress 是绕过脚本、直接循环 smoke 二进制得到的，等价于脚本行为。

### 2. 跨 Space 实机门控确定性失败（P1，未定性）

两次运行都在同一点失败：

```
CrossSpaceLiveTests.swift:100 XCTAssertEqual failed: ("[3]") is not equal to ("[320]") — Chrome must have opened on the second Desktop
cross-space live test: parked window spaces=[3] onScreen=true ... activeSpace=3 home=3 other=320
```

本机 main display 上确实有两个 user Space（3 和 320），测试先切到 320（该断言未报错），但 Chrome
窗口仍落在 3。需要先判定是 `SLSManagedDisplaySetCurrentSpace` 在 macOS 26.6.2 上不再真正切换
Desktop，还是 Chrome 忽略了目标 Space；在产品侧，这决定了「跨 Space 后台读取/点击/输入」这条
能力当前是坏的还是只是无法验证。

### 3. 钉钉 snapshot 性能异常（P1，性能样本）

AppMatrix 中钉钉单次 snapshot 23.7 s，park 后 22.2 s，restore 24.7 s，节点数 707。同轮对照：
Cursor 588 节点 2.9 s、飞书 485 节点 0.9 s、Finder 161 节点 1.4 s。这是
`tech-debt-tracker.md` 中「大型控件树 provider 耗时」的第一份具体实证。

### 4. Occlusion 实机门控首跑偶发失败（P2，测试竞态）

首跑在 1.5 s 内失败于 `OcclusionKeepAliveLiveTests.swift:59`：`Chrome is not a running application`。
该处直接对刚拿到窗口的 pid 调 `NSRunningApplication(processIdentifier:)`，没有重试；复跑（8.97 s）
通过。属于测试自身的启动竞态，不是产品行为回归。

### 5. AppMatrix 中 3 个 Chromium 系 app 输入未回读（P2，待复现）

| app | 结果 |
| --- | --- |
| Google Chrome | `field=AXTextField#55 click+type 177ms typed=false cleared=true` |
| 语雀 | `field=AXTextField#10 click+type 164ms typed=false cleared=true` |
| 钉钉 | `field=AXTextField#11 click+type 189ms typed=false cleared=true` |

飞书（`AXComboBox#411`）、系统设置、Clash Party 都是 `typed=true cleared=true`。`cleared=true` 在
从未输入成功时天然成立，所以这三条不能证明「输入后清理成功」。需要非 PARK 模式对照，区分是
PARK/虚拟屏副作用，还是 Chromium 页面在后台输入上的既有边界。

### 6. AppMatrix 中 3 个 app snapshot 报 `cgWindowNotFound`（P3，环境噪声）

微信、TextMate、iTerm2 三个 app 的 snapshot 都失败于 `Apple event error -10005: cgWindowNotFound`。
其中 TextMate 当前所有窗口都不在屏上；微信/iTerm2 的窗口模型不通过常规窗口路径暴露。矩阵应先
过滤「没有 on-screen 窗口」的 app，否则这类环境噪声会被误读成产品失败。

### 7. AppMatrix 指针位移断言失败（P3，疑似用户操作）

`the survey must not move the pointer`：起点 `(647.6, 250.6)`，终点 `(656.8, 296.8)`，位移约 46 pt。
该项需要在无人值守时复现才能定性（PARK/虚拟屏副作用 vs 用户移动鼠标）。

## 追加诊断（2026-11-11 下午）

1. **跨 Space 失败定性**：独立探针确认 `SLSManagedDisplaySetCurrentSpace` 只更新
   `SLSGetActiveSpace` 的返回值，在屏窗口集合切换前后完全一致（64 个窗口，0 个消失），
   即桌面没有真正切换。测试已改为识别 no-op 并 `XCTSkip`，不再误报产品失败。
2. **钉钉 23 s**：`snapshot.tree_walk` 占 19.6 s，采样显示时间全部阻塞在钉钉的 AX provider；
   完整证据与优化方向见 `dingtalk-ax-latency.md`。
3. **`typed=false` 非 PARK 对照**：语雀、钉钉在非 PARK 模式下仍然 `typed=false`，同轮 Mao 为
   `typed=true`，说明不是 PARK/虚拟屏副作用，而是这两个 app 的后台输入边界，需要单独定位；
   该轮 Chrome 因“没有空白输入框”未进入输入测试。
4. **指针位移**：非 PARK 对照轮位移达 165 pt / 323 pt，远超程序性抖动，且 click 默认不走
   global 指针回退（需要显式环境变量），判定为交互期间用户移动了鼠标。1 pt 容差的断言只在
   无人值守时才有判定意义。
